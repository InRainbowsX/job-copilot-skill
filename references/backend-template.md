# 后端岗位模板

当候选人的主要目标岗位是后端 / 服务端时，使用本模板。

当简历明显带有 `风控 / 反爬 / 设备指纹 / bot detection` 语境时，仍保持后端主路由，同时参考 [risk-control-backend-knowledge-base.md](./risk-control-backend-knowledge-base.md) 做更细的深挖与审核。
当这些案例需要按风控 / 反爬后端的高质量标准做包装与审核时，同时应用 [risk-control-backend-template.md](./risk-control-backend-template.md)。

## 模板目标

让候选人在简历和面试中呈现出“能解释系统、能讲清权衡、能落到稳定性和结果”的后端工程师画像，而不是只会做 CRUD 的开发。

## 1. 路由信号

强信号：

- Java、Go、Python、Node.js
- Spring、Gin、Echo、Django、FastAPI、Express
- MySQL、PostgreSQL、Redis、Kafka、RocketMQ、RabbitMQ、Elasticsearch
- 微服务、服务治理、API 设计、分布式系统
- 性能优化、稳定性、故障恢复、监控、容量、一致性

辅助信号：

- 订单、支付、库存、用户中心、调度、数据链路
- 延迟下降、QPS 提升、超时治理、重试、补偿

如果出现以下语境，不要把它改写成独立安全岗，而应视为后端子方向：

- 设备指纹、device intelligence
- 反爬、bot detection、content scraping 对抗
- 风险识别、策略引擎、实时判定
- 误杀 / 漏放 / 风控收益

## 2. Agent 1 深挖问题

优先挑选 1 到 3 个同时具备“系统复杂度、可量化结果、可解释 ownership”的项目。

建议按这个顺序深挖：

1. 这个项目解决了什么业务问题？
2. 你负责的是系统里的哪一部分？
3. 最大的流量、数据或复杂度挑战是什么？
4. 做了哪些设计或实现选择？
5. 为什么这么做，而不是更直观的替代方案？
6. 最终带来了什么可量化结果或运维改进？
7. 你实际处理过什么故障、风险或权衡？

后端岗位的必问补充：

- 服务边界、上下游依赖是什么
- 数据库或缓存是怎么设计的
- 是否用了异步链路或消息队列
- 瓶颈是如何定位出来的
- 稳定性或故障处理做了什么
- 结果是怎么衡量的

## 3. 包装规则

后端岗位优先包装这些方向：

- 在明确边界内体现系统 ownership
- 有可解释瓶颈的性能优化
- 带运维或稳定性思维的治理改进
- 把业务抽象成服务或模块的能力
- 工程 rigor：监控、重试、幂等、一致性、降级、兜底

安全的强化动作：

- 在有支撑的前提下，把模糊参与改成明确模块负责
- 把泛化的“做过优化”改成“瓶颈 + 方法 + 结果”
- 先讲业务或系统问题，再引出技术选型
- 在架构权限有限时，强调权衡和具体贡献，而不是硬写成架构 owner

高风险包装：

- 没有设计深度却写成架构主导
- 没有真实例子却写分布式一致性能力
- 虚构高 QPS、低延迟或高可用指标
- 把团队级平台成果写成个人 ownership
- 写了中间件和治理能力，但一追问就讲不清

## 4. Agent 2 后端审核补充

除通用 rubric 外，还要额外检查：

- 候选人能否解释系统边界和请求链路？
- 候选人能否解释为什么这样设计缓存、MQ 或数据库？
- 候选人能否讲出至少一个真实技术难点，而不是后端黑话堆砌？
- 这段表述是否符合候选人年限下可信的后端职责范围？
- 一旦追问性能、稳定性或一致性，故事会不会立刻崩掉？

必须降级表达的情况：

- 讲不清瓶颈是怎么定位出来的
- 分不清个人贡献和团队贡献
- 指标没有基线、没有方法、没有上下文
- 只是在装饰性地使用分布式系统词汇

## 5. 模拟面试主题

后端模拟面试建议轮转这些主题：

- 项目深挖
- 数据库与缓存基础
- 消息队列与异步设计
- 稳定性与故障处理
- 场景设计：库存、订单链路、幂等、重试、降级

高压追问示例：

- 为什么你选这个方案，而不是更简单的那个？
- 瓶颈到底出在哪一层？
- 如果流量翻倍，最先出问题的会是什么？
- 你怎么证明这次优化真的有效？
- 哪部分是你个人负责，哪部分是团队一起做的？

## 6. 期望输出形态

一个通过审核的后端项目故事，通常至少要清楚表达：

- 业务背景
- 服务或模块边界
- 技术挑战
- 设计或优化方法
- 可量化结果
- 稳定性意识或权衡过程
