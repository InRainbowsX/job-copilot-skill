# 冒烟失败处理闭环

当对话式冒烟测试发现一个新的问题时，不要只在口头里记住它。必须把它立即沉淀成 issue，再进入修复流程。

## 闭环目标

这条闭环要解决两个问题：

- 冒烟测试发现的问题不会丢失
- 修复工作继续遵守仓库现有的 issue / PR 治理规则

## 标准流程

### 1. 运行冒烟测试

按照 `references/smoke-test-checklist.md` 执行固定 prompt。

### 2. 识别是否出现新问题

如果出现以下任一情况，视为发现新问题：

- 关键行为缺失
- 出现了明确的禁止行为
- 输出与已有规则冲突
- 之前没有记录过的失败模式再次出现

### 3. 立即记录最小信息

最少记录以下内容：

- 失败的 smoke prompt
- 实际观察到的行为
- 预期行为
- 影响或风险

### 4. 先建 issue，再继续修复

发现新问题后，必须先创建 issue，再进入代码或文档修改。不要先“顺手修一下”，否则问题很容易脱离治理流程。

### 5. 按标准流程推进

新 issue 创建后，继续遵循仓库规则：

- 补齐 issue 的 `背景 / 要做什么 / 别做什么 / 什么算完成`
- 开分支
- 改动
- 本地验证
- 提 PR 并关联 issue

## 推荐工具

优先使用以下两种方式之一创建 issue：

- `assets/smoke-failure-issue-template.md`
- `scripts/create_smoke_issue.sh`

## 什么时候不用新建 issue

只有一种情况可以不新建：

- 该失败已在现有 open issue 中被明确覆盖，且你能准确指向那个 issue

如果不能明确确认已有 issue 已覆盖，就新建 issue，不要猜测。

## 结果要求

一个合格的冒烟失败闭环，应当做到：

- 问题能被复现
- 问题能被追踪
- 修复动作能回到治理流程
- 后续可以把问题沉淀进回归测试集
